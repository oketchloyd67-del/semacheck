Authentication and keys

Every request sends a secret key as a bearer token. Accounts hold multiple keys — up to 5 active secret keys and 3 active publishable keys — so you can run one per environment or per integration. Keys come in two modes:

  • sk_test_… / pk_test_… — sandbox keys. Deterministic test responses, no live data, no quota used. The Free plan includes these only.
  • sk_live_… / pk_live_… — live keys. Real checks against live data, metered against your plan's monthly quota. Any paid plan.
Authorization: Bearer sk_live_YOUR_API_KEY_HERE

Key security duties: keep secret keys server-side only (never in browser code, apps, or public repos); hash or encrypt them at rest; rotate by creating a new key and revoking the old one; never share live keys outside your organisation; tell us promptly if a key leaks so we can revoke it. Full duties are in the API terms.

Sandbox mode

The Free plan is a sandbox: it issues test keys only and makes no live checks. A sandbox /v1/check responds instantly, in the same shape as production, with "mode": "sandbox". The subject text picks the verdict, so you can build and demo every branch of your UI:

subject contains "scam" or "fraud" → verdict: reported (confidence 98) subject contains "suspect" or "caution" → verdict: caution (confidence 60) subject contains "unverified" or "unknown" → verdict: unverified (confidence 20) anything else → verdict: registered (confidence 55)

Sandbox calls never consume quota and never touch the report database. When you are ready, upgrade to a paid plan and switch the same integration to an sk_live_ key — the request and response formats are identical.

Pay-gating — charge per check

Two ways to put a M-Pesa payment in front of a check. Both need a live key (sandbox keys answer HTTP 402 sandbox_key) and both issue the same token:

  1. POST /v1/gate with { checkType, subject } — the gate for your own payment: the STK push goes to the M-Pesa number on your account, so your organisation pays for the check rather than your visitor. KES 30 per check, 15-minute window. If that number isn't set yet the call answers 402 billing_phone_missing — add it in the API dashboard.
  2. POST /v1/paid-check with { checkType, subject, phone } — charge an end user KES 30 by STK push inside your own checkout, then poll the same token.
  3. Both return a checkToken; the payment callback releases the verdict.
  4. POST /v1/token/verify with { checkToken } until status is paid, then read the verdict. Responses: awaiting_payment → paid (verdict included), or consumed if already delivered once. Expired or failed windows answer HTTP 402 with token_expired or payment_failed — open a new token.
POST /v1/gate → { "checkToken": "chk_…", "status": "awaiting_payment", "payer": "account", "priceKes": 30, "expiresAt": "2026-10-15T14:22:00Z" } POST /v1/token/verify → { "status": "paid", "verdict": "reported", "confidence": 72, "reasons": [ … ] }

Pay-gating needs a live key — sandbox keys answer HTTP 402 sandbox_key.

Verdict values and fail-open vs fail-closed

reported Reported — proof points exist.
caution Caution — something is off.
registered Registered — matches a known public record.
unverified Unverified — nothing yet says either way.

These four are the entire public vocabulary — the website, the docs, the Verified programme and the API all use exactly this list, and displayVerdict carries the matching title case (Reported, Caution, Registered, Unverified). Anything else you see in older data is a legacy spelling of one of these four.

Fail-open or fail-closed is your product decision, not ours. A verdict is a point-in-time signal, not a guarantee. If your API call fails (network, 5xx), we recommend failing closed for money-moving flows — ask the user to wait or try again rather than proceeding unchecked. For unverified verdicts, most partners fail open with a lightweight warning. Never treat a verdict as the sole reason to refuse a person service; see the API terms.

Rate limits, quotas and error shape

X-RateLimit-Limit: 60 X-RateLimit-Remaining: 41 X-RateLimit-Reset: 23 X-Quota-Limit: 2000 X-Quota-Remaining: 1987 X-Request-Id: abc123

Errors are JSON with a machine-readable error code and, where useful, a human message. Field names are always camelCase; error codes are fixed lowercase values you can switch on:

HTTP 400 { "error": "missing_parameter", "message": "checkType and subject are required." } HTTP 401 { "error": "invalid_api_key" } HTTP 402 { "error": "upgrade_required", "message": "Live checks are not included in the Free (sandbox) plan…" } HTTP 402 { "error": "plan_expired", "message": "Your API plan is suspended. Live keys are temporarily blocked until the account is current…" } HTTP 402 { "error": "account_pending", "message": "This API account is still under review…" } HTTP 402 { "error": "token_expired", "message": "The 15-minute payment window elapsed…" } HTTP 402 { "error": "rate_limited", "message": "Too many M-Pesa payment prompts were started for this phone in the last hour (3)…", "retryAfter": 3600 } HTTP 402 { "error": "batch_not_enabled", "plan": "Starter" } HTTP 429 { "error": "rate_limited", "retryAfter": 60 } HTTP 429 { "error": "quota_exceeded", "quotaLimit": 2000, "checksUsed": 2001 } HTTP 500 { "error": "check_failed", "message": "…" }

HTTP 402 always means "pay or wait" — upgrade your plan, settle an overdue invoice, or complete a pending gated payment. It is never an authentication failure (that is 401).

Renewal, reminders and grace period

Paid plans renew monthly on your plan date:

  • We email a renewal reminder 3 days before the renewal date.
  • An unpaid plan enters past_due on the renewal date. You then have a 7-day grace period during which live keys keep working.
  • After the grace period the account is suspended and live keys answer HTTP 402 plan_expired. Settle the invoice (or re-buy the plan from the dashboard) to reactivate. Suspension is never an authentication failure — a valid key that is blocked for billing answers 402, so you can tell "settle or wait" apart from "wrong key" (401).
  • Billing states never block sandbox work: sk_test_ keys keep working on pending, past_due and suspended accounts. Only a closed account answers 402 for every key.

Webhooks

The Growth and Scale plans send signed POST requests when a watched subject changes verdict.

POST https://your-server.com/webhooks X-SemaCheck-Event: subject.verdict_changed X-SemaCheck-Signature: t=1760000000,v1=9f2b…e41c { "event": "subject.verdict_changed", "created_at": "2026-10-04T11:02:10Z", "data": { "type": "phone", "value": "254712345678", "previousVerdict": "unverified", "verdict": "reported", "confidence": 72 } }

Verify X-SemaCheck-Signature (t=timestamp,v1=hmac-sha256 of timestamp.body with your webhook secret) and reject replays older than 5 minutes.

Widget guide

Embed one script tag; the widget renders a "Check before you pay" box on your page. Publishable keys (pk_test_/pk_live_) are designed for browsers and are locked to the domains you register in the dashboard.

<script src="https://semacheck.vercel.app/widget/semacheck-widget.js" data-key="pk_live_YOUR_KEY" data-types="phone,paybill" data-theme="light" data-target="#semacheck-check" async></script> <div id="semacheck-check"></div>
data-key — required. Your publishable key (pk_test_… or pk_live_…).
data-types — comma list of allowed check types: phone,paybill,business,website,job. Default phone,paybill.
data-theme — light (default) or dark.
data-target — CSS selector where the widget mounts. Default #semacheck-check.

See a live example at /widget/demo.html. The widget's checks spend your plan quota like any other call.

Organisation verification

API accounts verify their organisation — a business registration number plus the registration certificate (JPG, PNG or PDF), reviewed by our admin team. Verified organisations can buy paid plans and use live keys. Start from the API dashboard.
